# Native Markdown 内存诊断与优化记录（2026-08-31）

## 结论摘要

这次调查始于一个反直觉现象：Typora 使用 Electron，而运行一段时间的 Native Markdown 看起来占用了更多内存。最终结论不是“原生技术天然输给 Electron”，而是最初比较混入了进程生命周期、统计口径和应用行为差异。

在同一份中文书稿尚未滚动加载后续图片的初始状态下，新的 Native Markdown release 进程稳定在约 87 MiB 私有字节、68 MiB 私有工作集；当时 Typora 的 4 个进程合计约为 374 MiB 私有字节、110 MiB 私有工作集。异常的 Native Markdown 实例则已运行较长时间，私有字节约 290 MiB、私有工作集约 266 MiB，历史工作集峰值约 891 MiB，不能直接拿它与新启动的 Typora 或单个 Typora 子进程比较。

调查先后确认并处理了四类问题：

1. 缺少可重复、可失败的真实进程内存基准；
2. 每秒后台维护无条件请求重绘，以及状态栏随每次渲染重复分析 Markdown；
3. 高精度滚轮会产生大量细碎字号，放大 GPUI/DirectWrite 文本排版缓存和分配器高水位。
4. TextView 虚拟列表的图片请求会穿过祖先图片缓存的动态作用域，造成全局原图与文档缓存并存，而且切换文档时全局图片没有释放。

文本路径修复后，当时覆盖的空闲、视图、缩放、重开和滚动场景均通过 160 MiB 峰值预算。最重的分栏缩放场景约为 124.8 MiB 私有字节、105.4 MiB 私有工作集；空闲 5 秒只增长约 0.02 MiB。后续完整加载 10 张大图的独立压力场景采用更符合图片工作负载的 230 MiB 私有字节预算，实测峰值约 183.5 MiB，切换纯文本后约 137.6 MiB。

因此，项目仍有继续开发的价值。更准确的产品判断是：Native Markdown 已有比 Typora 更低的基础内存，但必须持续管理文本排版、图片和长生命周期缓存，不能把“使用 native 技术”本身当作性能保证。

## 调查范围与口径

### 测试文档

调查使用的文件为：

```text
E:\data_z\BOOK\ing\Build-A-Large-Language-Model-CN-main\cn-Book\1.理解大语言模型.md
```

文件特征：

- 29,224 字节；
- 278 行；
- 以中文正文为主；
- 包含 10 个本地 PNG 引用，源图宽度约为 2,096–3,178 像素，总计约 4,450 万源像素。

早期调查曾把这份文档误判为“无图片文档”。真正原因不是文件没有图片，而是最初的自动滚动把 `WM_MOUSEWHEEL` 坐标写成 `(0, 0)`；消息虽然被 Windows 接受，却没有命中预览区域，所以没有滚到后续图片。早期文本、缩放和空闲结论仍然有效，但“图片已被排除”的结论无效。2026-09-01 的补充调查修正了滚轮坐标，并增加了同进程切换纯文本文档的图片释放场景。

### 内存指标

报告同时记录三个 Windows 进程指标：

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| Working set | 当前驻留在物理内存中的全部页面，包含共享页面 | 观察用户在任务管理器中大致会看到的驻留规模 |
| Private working set | 当前驻留且为进程私有的页面 | 跨单进程与多进程应用比较时更有参考价值 |
| Private bytes | 进程已提交的私有虚拟内存 | 观察堆、缓存和分配器高水位，通常比工作集更早暴露长期增长 |

比较 Electron 应用时必须汇总主进程、渲染进程和辅助进程。只比较 Typora 的一个进程与 Native Markdown 的唯一进程，会系统性低估 Electron 的总成本。

## 可能方向与假设树

调查开始时保留了以下方向，没有先入为主地认定某一个框架或模块有错：

1. **比较口径错误**：Electron 多进程没有求和，或混用了 Working set 与 Private bytes；
2. **debug/release 差异**：调试构建、符号或日志导致常驻内存偏高；
3. **图片缓存**：原图解码、缩放副本或 GPU 纹理未释放；
4. **周期任务**：每秒定时器无条件重绘，逐渐扩大渲染缓存；
5. **重复 Markdown 分析**：状态栏、目录或搜索在每帧重新解析全文；
6. **TextView 重建或重解析**：渲染函数每次构造 `TextView::markdown`，可能重复生成解析树；
7. **视图切换或重新打开**：预览、源码、分栏之间切换时旧状态被保留；
8. **滚动虚拟化失效**：滚过的段落都永久留在内存；
9. **字体回退**：系统 UI 字体不覆盖中文，DirectWrite 为大量汉字建立昂贵的回退数据；
10. **多字号排版缓存**：缩放为每个字号生成新的行布局、字符宽度或字形缓存；
11. **GPU 图集**：不同字号对应的 glyph atlas 不释放；
12. **分配器高水位**：对象已经释放，但堆提交页面没有及时归还操作系统。

这些方向中，有些可以直接修复，有些必须先用场景隔离和反证实验排除。

## 诊断工具与可重复基准

第一阶段没有直接改业务逻辑，而是增加了 Windows 真实进程基准：

- Rust 端通过 `GetProcessMemoryInfo` 采集 Working set、Private working set 和 Private bytes；
- PowerShell 脚本为每个场景启动全新的应用进程；
- 基准输出稳定的机器可读记录，并用退出码表示通过、预算失败或基准自身错误；
- `scroll` 场景向真实窗口发送 `WM_MOUSEWHEEL`，不是只调用内部函数；
- 默认预算为 160 MiB 峰值私有工作集、160 MiB 峰值私有字节、80 MiB 私有字节增长。

## 排除过程

### 1. debug 构建不是主要原因

新启动的 debug 与 release 进程基线只相差约 1 MiB 私有字节。调试构建会影响二进制大小和执行性能，但不能解释从约 87 MiB 到约 290 MiB 的长期增长。

### 2. 早期基准没有真正覆盖图片路径

最初的滚动消息没有命中预览区域，因此没有触发后续图片加载。这个阶段只能说明“纯文本路径稳定”，不能说明图片不是增长源。修正输入坐标后，滚过全部图片可以稳定复现 275 MiB 左右峰值，以及切换到纯文本后仍保持约 232 MiB 私有字节的问题。完整排除和修复过程见后文“图片密集场景补充调查”。

### 3. 空闲、滚动、切换视图和重开都没有复现增长

隔离场景显示：

- 空闲稳定在约 87 MiB 私有字节；
- 滚动稳定，消息全部被窗口接受；
- Preview、Split、Source 循环切换只产生少量增长；
- 重复打开同一文件同样稳定。

因此，没有证据支持“虚拟列表会永久保留所有滚过内容”或“每次打开文件都泄漏一份完整文档”。

### 4. 缩放是稳定的放大器

旧缩放探针从 50% 开始，以 10% 为一级切换多个字号。在 release 下：

- 1 个阶段后约为 150 MiB 私有字节；
- 2 个阶段仍约为 150 MiB；
- 3 个阶段上升到约 181 MiB；
- 5 个阶段约为 182 MiB。

增长随后趋于平台，而不是每一步都线性无界增加。这更像排版缓存和堆高水位，而不是应用层 `Vec` 每次泄漏一份内容。

Preview、Source 和 Split 都能复现，说明问题不只属于 Markdown 解析器；源码编辑器同样会受底层文本排版影响。

### 5. 中文是强放大器，但“字体回退”假设被否定

同样的源码缩放测试换成 2,165 字节的英文 README 后只增长约 7 MiB，而中文书稿会增长数十 MiB。因此，文档长度、汉字数量和中文排版是明显放大因素。

一个合理猜测是 `.SystemUIFont` 本身不包含中文，DirectWrite 的逐字符字体回退造成额外缓存。为验证它，曾将正文主字体临时改为系统已安装且覆盖简体中文的 `Microsoft YaHei UI`，再运行完全相同的 release 缩放基准。结果几乎不变：仍约为 162 MiB 私有工作集、182 MiB 私有字节。

因此，不应为了本问题把字体强制改为微软雅黑。显式中文字体可能改变视觉效果和跨平台行为，但没有解决所测内存增长。

### 6. “每次 render 都重新解析 Markdown”不是事实

应用确实会在 render 中构造一个 `TextView::markdown(...)` 壳对象，这看起来可疑。但检查 `gpui-component 0.5.1` 源码后确认：

- TextView 使用固定 key `native-markdown-preview/state` 复用 `TextViewState`；
- 原文未变化时，`Update::Text` 不触发重新解析；
- `TextViewStyle` 未变化时，`Update::Style` 也不触发重新解析；
- 真正变化的文本或样式有 200 ms 合并延迟。

因此，把临时 `TextView` 壳保存在应用状态里既不能消除已存在的解析，反而可能干扰组件内部任务和 keyed state 生命周期。这个方向被明确放弃。

不过，检查 render 路径时发现了另一个真实问题：状态栏每次渲染都会调用 `markdown::word_count`，而它会再次运行 `pulldown-cmark` 并构造纯文本。这成为最终优化的一部分。

### 7. 主要增长位于 CPU 堆，不是 GPU 图集

对异常实例的 VMMap 检查显示，显著增长集中在已提交 heap 和 private heap working set，而不是能够直接归因于纹理的 GPU 区域。GPU glyph atlas 仍可能参与渲染成本，但没有证据表明它是这次约 200 MiB 差额的主因。

### 8. 旧缩放基准混入了 50% 极端行为

进一步分层后发现，从正常 100% 向上缩放的行为明显不同：

- 100% 开始的 5 个阶段只增长约 1.7 MiB；
- 10 个阶段增长约 31 MiB；
- 从 100% 运行到 250% 再回落的 30 步压力测试，最终约为 120 MiB 私有字节，增长约 33 MiB。

50% 会让同一视口显示更多中文内容，也会改变虚拟列表可见范围和换行布局，因此它是有意义的极端压力场景，但不应被伪装成“正常缩放的第一步”。最终基准改为从 100% 出发；50% 仍作为需要单独观察的边界，而不是被宣布为已经消失。

## 最终原因判断

以下是有直接证据支持的事实：

- 新启动 Native Markdown 的基础内存低于 Typora 多进程合计；
- 空闲、滚动、视图切换和重开不是本次长期增长的主要复现路径；
- 中文长文档的多字号布局是稳定放大器；
- 强制使用中文主字体没有改善；
- TextView 未在每次 render 重新解析相同 Markdown；
- CPU heap 是主要增长区域；
- 50% 的可见内容密度会显著提高一次性内存高水位。

结合 GPUI 源码，可以作出以下高可信推断：

- GPUI 的文本系统按 `FontId + font_size` 保留 `LineWrapper` 池，每个 wrapper 又会缓存 ASCII 与其他字符宽度；
- DirectWrite 和窗口级行布局还会为实际使用的字号进行 shaping、换行和 glyph 处理；
- 高精度滚轮原先会产生 103.5%、103.8% 等大量不稳定字号；
- 即使相关布局对象后来释放，Windows 堆分配器也未必立即把已提交页面归还系统，于是长期实例表现为较高 Private bytes 和 private working set。

这不能证明 GPUI 或 DirectWrite 内部某一个具体 map 在“泄漏”，但足以说明应用不应把连续滚轮输入原样映射为无限多的实际字号。最终修复采用有界字号集合，而不是依赖无法从公共 API 清理的内部缓存。

## 最终优化方法

### 1. 只在可见状态变化时请求重绘

后台任务仍然每秒检查恢复文件和通知过期，因为这些行为需要时间驱动；但 `run_background_maintenance` 现在返回“可见状态是否改变”，只有返回 `true` 时才调用 `cx.notify()`。

这避免了文档完全静止时每秒无条件重建 UI 元素树和请求渲染，同时不牺牲通知自动消失与恢复状态更新。

对应提交：`a20c68b perf: avoid redundant document rerenders`。

### 2. 将阅读统计绑定到文档变化，而不是 render

`word_count` 和 `reading_minutes` 现在是 `NativeMarkdownApp` 的缓存字段。打开、新建、恢复或编辑导致文档变化时，`refresh_analysis` 统一更新：

- 预览使用的 `SharedString`；
- 标题目录；
- 字数；
- 预计阅读时间；
- 搜索结果。

状态栏只读取缓存，不再为了显示两个数字而反复解析整份 Markdown。

对应提交同样为 `a20c68b`。

### 3. 累积滚轮输入，但只应用 10% 稳定字号

`ZoomLevel` 现在区分：

- `gesture_factor`：连续累积触控板或高精度滚轮的细小输入；
- `applied_factor`：真正交给 Theme 和文本系统的字号倍率。

手势可以连续积累，但只有越过最近的 10% 档位时才更新 `applied_factor` 并触发重排。例如，连续两次 3.5% 放大可以最终落到 110%，而不会先后创建 103.5% 和 107.1% 两套排版缓存。键盘缩放与手势缩放因此共享同一组 50%–250% 的 10% 档位。

对应提交：`95856dd perf: bound zoom text layout cache growth`。

### 4. 让缩放基准描述真实路径

缩放基准现在从 100% 开始，逐级上升到 250% 后回落。这样它仍覆盖多个实际字号和三种文本表面，却不再把直接跳到 50% 的极端可见密度当成正常第一步。

50% 场景没有被忽略：旧探针数据保留在本文，并列入后续独立压力测试方向。

## 没有采用的方案

### 强制中文字体

实测无改善，并会改变排版观感与跨平台字体策略。除非未来有字体缺字或一致性需求，否则不应以“节省内存”为理由采用。

### 将 TextView 存进应用状态

组件已经通过 keyed state 复用解析结果。保存外层临时 element 不会减少解析，还可能破坏内部异步任务的生命周期。

### 取消每秒维护任务

通知过期和恢复文件状态确实需要周期检查。正确优化是没有可见变化时不请求重绘，而不是删除功能。

### 因一次异常实例立即更换 GUI 框架

新进程基线和多进程总量证明，框架结论不能由任务管理器中的一个数字得出。更换框架成本高，也不会自动消除应用层重复工作、图片预算或字体排版缓存。

## 边界与未决问题

1. **50% 极端缩放**：旧实验可达到约 150–182 MiB 私有字节。它更接近一次性高水位而不是持续泄漏，但仍高于当前 160 MiB 默认预算的一部分测次。
2. **分配器不主动回落**：Private bytes 不下降不等于对象仍可达。若产品要求缩放后立即归还内存，需要 heap allocation trace 或上游缓存释放接口，而不能只观察任务管理器。
3. **单机数据**：当前数字来自一台 Windows 机器和一套字体/显卡驱动，绝对值不应作为所有设备的保证。
4. **Typora 是动态对照**：Typora 的扩展、窗口、后台任务和版本都会改变多进程数据。本报告记录的是当时对照，不是永久的产品排名。
5. **图片格式范围**：新增的预处理针对本地 PNG/JPEG；动画图、SVG 和远程图片保持原路径，仍需独立压力测试。
6. **CPU 与帧时间尚未纳入门禁**：减少无效 notify 理论上同时降低空闲 CPU，但本轮自动门禁只检查内存。

## 后续可行方向

按投入产出比排序：

1. **增加长时间 soak 场景**：连续滚轮缩放、正反滚动、切换视图和重复打开文档运行 10–30 分钟，记录峰值而非只看终点。
2. **保留独立的 50% 压力场景**：不要改变正常缩放回归的语义，同时监控低倍率下同屏内容翻倍带来的高水位。
3. **扩展图片密集基准**：现有场景已覆盖完整滚动与文档切换；后续增加动画图、远程图片、超宽窗口和反复切换的 soak 测试。
4. **记录空闲 CPU 和帧时间**：将每秒无效重绘的优化转化为可回归指标，至少记录 CPU 时间增量和渲染帧数。
5. **使用 ETW/WPA 或 heap profiler**：若再次出现 250 MiB 以上的长期实例，应捕获分配调用栈，而不是继续根据最终堆大小猜测。
6. **研究局部缩放**：目前修改全局 Theme，会让工具栏、状态栏和文本表面一起重新布局。如果 GPUI 提供可靠的局部 text style 或视觉 transform，可只缩放文档表面。
7. **推动上游缓存边界**：评估 GPUI `wrapper_pool`、DirectWrite 行布局和字形缓存是否需要容量限制或显式清理 API；应用层不应依赖私有实现细节打补丁。
8. **获取公开的 TextView 滚动句柄**：有了可控 `ListState`，可以更精确地自动化整篇滚动、定位可见节点，并区分虚拟列表和文本系统成本。

## 图片密集场景补充调查（2026-09-01）

### 用户可见症状与红色基准

补充调查使用同一份多图书稿，并在同一应用进程内切换到纯文本文件：

```text
多图：E:\data_z\BOOK\ing\Build-A-Large-Language-Model-CN-main\cn-Book\1.理解大语言模型.md
纯文本：E:\data_z\BOOK\ing\Build-A-Large-Language-Model-CN-main\_sidebar.md
```

新增的 `image-release` 场景会：

1. 启动多图文档；
2. 读取窗口实际矩形，将滚轮消息发送到窗口中心，持续向下滚动；
3. 在指定 step 调用真实的打开文件路径，在同一进程切换到纯文本；
4. 同时记录图片实际读取次数、文档缓存估值、峰值与切换后的最终内存。

修复前可重复数据为：基线约 86.79 MiB，峰值约 275.27 MiB，切换纯文本后稳定在约 231.86 MiB；文档图片缓存只报告约 26.61 MiB，实际读取次数却达到 11 次，超过文件中的 10 个唯一图片引用。这个“计数超过唯一图片数、缓存估值远小于进程增长”的组合，成为定位第二条加载路径的关键证据。

红色基准提交：`84f3ed6 test: reproduce image memory retention`。

### 假设与排除过程

调查依次验证了以下方向：

1. **GPUI 全局资产缓存保留原图**：得到支持。虚拟列表确实会走 `ImgResourceLoader` 全局路径。
2. **先完整解码原图再缩放造成瞬时峰值**：只解释部分峰值。把自定义缓存改成流式 PNG 缩放后，整体结果几乎不变，因为另一条全局路径仍在完整解码原图。
3. **文档缓存的 `drop_image` 没有释放 GPU 纹理**：不是主因。GPU 性能计数器只显示约 12.5 MiB 共享 GPU 内存；主要增长仍在 CPU 私有提交内存。
4. **Windows 堆只是不主动归还页面**：单独调用 `HeapCompact` 后最终值仍约 224 MiB，不能解释大部分滞留，因此没有保留这个平台专用补丁。
5. **旧 TextView 解析状态保留整份文档**：没有独立证据支持。真正异常首先发生在图片资源加载边界。
6. **把图片宽度硬限制为 1,024 像素即可解决**：单独实施时只改善约 4 MiB，因为未经过文档缓存的全局原图仍存在；这个方案也被撤回。

诊断期间加入过短期 `[DEBUG-*]` 探针，记录 HTTP 图片读取、自定义缓存命中/未命中和流式解码完成时的进程内存。探针揭示的顺序是：同一 URI 先通过全局路径读取，随后自定义缓存再次读取；切换文档并清空自定义缓存后，旧 URI 仍可能从全局路径被访问。所有临时探针在提交前均已移除。

### 最终原因

GPUI 的祖先 `image_cache(...)` 通过窗口栈在子元素的布局/绘制调用期间提供缓存。`gpui-component` 的 `TextView` 开启滚动后使用虚拟列表，列表项会在延后的根布局中创建 `img(...)`；此时祖先缓存作用域已经退出。于是同一张图片出现两条路径：

```text
TextView 虚拟列表图片
├─ 延后布局：GPUI 全局 ImgResourceLoader → 保留按源尺寸解码的图片
└─ 祖先缓存可见的阶段：BudgetImageCache → 再次读取、解码并缩放
```

原实现切换文档时只清空 `BudgetImageCache`，没有删除 `ImgResourceLoader` 的全局资产。因此，文档缓存估值会下降，但全局 CPU 像素缓冲和关联纹理仍然存活，表现为打开纯文本后内存不降。

这也解释了为什么早期的流式解码实验无效：它只优化了树的下半支，而占用更大的全局原图分支没有改变。

### 最终优化方法

最终修复同时处理峰值、重复解码和文档切换释放：

1. **跟踪并显式释放文档图片资产**：`DocumentImageRoot` 去重记录实际请求过的 URI。打开、新建、恢复或另存为改变图片根目录前，应用同时清空文档缓存、调用 `drop_image`，并从 GPUI 全局 `ImgResourceLoader` 缓存移除对应资源。
2. **在全局解码之前准备本地大图**：本地 PNG/JPEG 在交给 GPUI 前按实际物理视口缩小，最大宽度为 1,280 像素。图片准备串行执行，避免多个大源图同时展开；不支持或无法解码的格式原样透传。
3. **共享全局解码任务**：`SizedImageAssetLoader` 不再直接调用 `ImageAssetLoader::load` 产生第二次解码，而是通过 `fetch_asset::<ImgResourceLoader>` 复用已经存在的任务和 `Arc<RenderImage>`。
4. **阻止过期异步任务回填**：每次切换文档递增 generation。旧文档仍在进行的图片任务可以自然结束，但不得把结果插入新文档的准备缓存，也不得增加新文档的加载计数。
5. **避免 UI 切换等待图片解码**：清缓存与耗时图片准备使用不同的锁；切换文档只清理轻量 map，不会等待正在后台执行的解码完成。

实现提交：`f302799 perf: release and bound document image assets`。

最终长测运行 22 秒，在切换前留出约 18 秒滚动和加载，确认 10 个唯一图片全部完成读取：

| --- | ---: | ---: | ---: |

### 仍可继续的方向

1. 向 `gpui-component` 上游提交 TextView API，使虚拟列表中的每个 `img` 能显式携带 `ImageCache`；这样可以删除当前对全局路径的兼容处理。
2. 对 PNG 使用真正的逐行缩小，在准备阶段避免最大单张源图的完整 RGBA 临时缓冲。当前串行准备已经限制并发峰值，但单张图仍会形成短暂高水位。
3. 将图片峰值预算按视口像素、图片数量或格式分类，避免用纯文本的 160 MiB 门禁机械衡量图片压力场景。
4. 增加连续打开多份多图文档、窗口反复缩放、动画图和远程图片的 10–30 分钟 soak。
5. 如果最终值在其他机器仍明显偏高，使用 ETW/WPA 采集切换前后的 heap allocation stack，区分 TextView 旧节点、解码器临时缓冲与分配器保留页。
